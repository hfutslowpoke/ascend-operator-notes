## 有价值的技术积累

**真实输入组织和完整数学链。** group_list 是实际累计边界，可能不均匀且含空专家。完整 true-K INT32 点积/归并后进入 FP32 scale、GELU，最后输出 FP16；原始行序、连续 ND、所有有效元素必写。早期的中间 half 路径在官方澄清后撤回，最终选用严格链路。未来应在设计开始就明确转换发生在哪一步。

**生产消费供给的结构性收益。** C0/C4 的宽 B 供给、较窄 N 消费、完整 A 驻留、延期 FIX 和独立 credit，改变了供数复用与在途计算。C0 旧载体两组平台观察从约 48.69/49.40 降到 42.52/43.60 µs；C4 同包一次明显改善、一次接近持平，证据强度不同。不能用同包 C0 的成功替代 C4 的重复验证。

**PMU 能否定错误假设。** R2 宽供给路径 sample 40.80→36.76 µs、另一分布 44.18→42.40 µs，关键组 MTE2 缩短；C1 v2 对随机长尾比均分显著有效。比只看 Cube busy 百分比，更有价值的是对应同一任务链的搬运、ready 等待、实际 owner 负载。

**生命周期是可独立推导的设计变量。** 保留了 R3 v4 的 A1/A2/B1/B2/L0C/GM-C 逐缓冲 ready 与最后读者 credit。它在不改 AIV 消费数学的条件下，先发 A、先发两个已就绪 MMAD，再等待未来 K。短本地对照约改善 1.9%–2.6%，尚无平台证据。这个例子适合以后研究按事件释放，而非只会套固定双缓冲。

## 为什么很多方向没有转化为平台收益

1. **减少局部工作，却把最终瓶颈移到别处。** C4 partial768 降低某些供数压力，却增加中间 C 往返和消费负担，完整耗时明显变差。I5 输出 MTE3 指令从 618 降为 185、输出搬运统计少约 13.2%，但就绪更晚、Vector/供数膨胀，生产六组几何反而慢 7.43%。结论应以完整调用为准。
2. **总字节下降，关键核反而更重。** R1 M64 将 A/B 总有效读从 40 KiB 降至 24 KiB，却使最大单核搬入及单 AIV 工作增加，几何慢约 15.99%。R3 pair128 的 L1→L0B 模型字节少约 26.5%，随机输入仍慢 2.26%。不能用总量代替最长依赖路径。
3. **本地输入和真实分组分布不匹配。** C1 official2 近乎无收益，random9181 改善约 33.7%。只围绕均匀输入做优化会漏掉长尾；只取有利随机输入又会过拟合。应固定多种真实 GL 分布、数值区间和随机种子，而非猜平台生成规则。
4. **局部组件性能不等于整合二进制性能。** 代码接入后可能改变分路、布局、模板实例、资源分配和事件压力。旧消费者的最低值不属于新消费者；私有 SDK 里的模式更快，也不能证明完整提交使用相同路径。源码、Host 选择、生成 ELF 和实际执行入口应形成闭包。
5. **隐藏点整包成绩受到其它点波动与评分尺度变化影响。** 单目标换一个点的源码仍会重新采样所有点；总分涨跌不足以断言目标隐藏点收益。后来所有点开放时，应立即转向逐点时间判断，历史分数不要跨时期混算。
6. **没有足够早地比较算法族。** 大量时间用于既有流水内的 tile、队列、指令重排，K=1、N=1、实际分组调度等退化/特殊结构没有及时形成完整的成本驱动覆盖。公开领先代码提供了值得补齐的路线，但未做平台消融前不能说它们解释全部分差。

## 多级 roofline 和 PMU 的正确位置

Roofline 用于排除不可能、定位哪层可能受限，并非给一个输入量除以峰值就得到“地板”。本次目标为 910C 单 die 的 20 AIC / 40 AIV、L1 512 KiB、L0C 128 KiB、UB 192 KiB；不应使用整卡默认峰值解释本 die。

需要分别记录申请容量、活跃地址集合、逻辑请求字节、真实层次事务。I5 的 AIV 读 L2 命中率接近 99.81%，因此“C 经 GM 往返”不直接等于“HBM bound”。FP32 GELU 中 Exp/Div 也不能简单当作普通 FLOP。

PMU 深采集会扰动 Task。不同核心的最大 Cube/MTE2/Vector 时间可重叠，不能相加或直接相减。普通 Task、PMU Task、平台微秒分别成表；对关键 owner 的同核同阶段做比较，再用最终 Task 验证。详见 [历史分层分析](../evidence/main-five-pmu-roofline.md)。

## 工程与协作教训

- **编译预算应作为资源约束。** 曾出现模板过多、源码接近 512 KiB、全包编译 443–466 秒逼近 600 秒限制。保留通用族与有效候选，及时移除未启用历史实现；格式化且只保留必要宏。最终版构建约 75.55 秒，不能把所有历史编译时间混在一起。
- **先编译实际要提交的整包。** 最后一次 C1 v2 + R3 v4 集成因 C++ 定义顺序失败。逆向提取能证明改动范围，却不能证明前置声明/定义依赖成立。只做了顺序修复的 ffd560… 后来编译通过，但没有再提交。应在每次 POST 前做一次实际载体完整编译，避免用平台机会发现纯工程错误。
- **最优索引必须带证据与载体。** 单个极小值、未验证本地优选、旧阶段的平台通过版要分别登记。owner、SHA、SID、测量时期、目标点和回退条件缺一项，后续集成容易误选。
- **NPU 串行，CPU 设计可并行。** 独立工作区避免互相改文件；NPU 锁保证计时不受其它 agent 运行污染。多 agent 的有效产出应是可编译组件、同口径对照和接入说明，而非重复审计或多个相似微调。
- **清理必须保护证据闭包。** 源码、日志、最终 ELF 身份、选中报告、哈希清单是长期资产。临时输入/构建和大型 PROF 可限时保留，但不能只凭“4 小时”删除仍被活跃实验引用的文件。
- **平台脚本的提交和成绩归属是独立问题。** 2 分钟、等结果、6 分钟、最终账号 3 分钟冷却等策略曾变化。应持久化 accepted SID；用 SID/服务器时间归属成绩；明确 429 与响应不明的区别，避免不明 POST 盲重试。

## 下一次的工作顺序

第一阶段先建立合法完整 baseline、环境身份、可复现 Task 计时和分布覆盖，覆盖极小输入、K=1、N=1、长 K、宽输出、非对齐尾部、空/长尾专家。提前建立算法族成本表，避免从一种 GEMM 内核开始无穷调参。

第二阶段对每个高耗时族画完整生产消费图，标出实际 owner、首包、持续供给、最后输出；测分层吞吐和关键等待。每个方向至少给出要减少的关键路径、额外工作和容量不等式，选择可能改变总工作量或有效重叠的方案。

第三阶段只用真实可提交载体验收：数学边界、随机与真实分组、完整编译、完整 Task、必要 PMU、平台逐点结果。固定父本和单目标；先登记日志再晋升索引。新候选即使平台未证优也可留存，但不得覆盖明确更强的平台版。

收尾阶段优先保证一个合法可编译的全包代表，留出提交冷却和结果回收时间。最后半小时不再把未完整构建的候选当作必交版本。所有结论按“静态推导 / 本地计时 / PMU / 平台单次 / 平台重复”注明证据。
