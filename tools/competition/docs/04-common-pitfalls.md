# 这类算子开发最常见的坑

按“最容易让成绩归零/白干”的顺序排列。

## A. 规则与提交

### A1. 把“能跑过公开用例”当成“域内正确”

平台会在赛后对排名靠前的 kernel 做 fuzzing。只对公开 shape/输入正确的特化，可能被判 R1/R5。

正确做法：

- 按题目声明的 shape/dtype/attr 域设计通用路径；
- 特化分支必须有正确 fallback；
- 对域内随机输入、边界输入、重复/非法索引做验证；
- 不要用 hash(shape)、指纹、白名单识别测试用例。

### A2. 把计算搬到 host

host 只允许：tiling、workspace 分配、memcpy、launch、shape/attr 校验。任何“先在 CPU 算好再拷回 device”的做法都违反 R2。

CPU 参考实现可以保留用于自测，但不能被 kernel 调用，不能作为输出回退，不能参与评分路径。

### A3. 结果重放 / 假计算

以下都违规：

- 复用预存 golden；
- 只读不写；
- 读无关 buffer 后 return；
- 在 UB/L2 算对但不写回 GM；
- kernel 为空操作或纯 DataCopy；
- 用历史输出覆盖当前输出。

### A4. 重复提交同一源码

同一源码改 ZIP 名、时间戳、注释再提交，通常没有收益，还可能被平台按重复处理。每次提交前用源码 digest 去重。

### A5. POST 后重发

POST 超时但没拿到 SID 时，先查提交历史，确认是否已受理；不要直接重发。拿到 SID 后只 GET。

### A6. 忽略“最近一次提交覆盖”

有些赛事采用最近一次提交，差包会覆盖好包。提交前确认当前队伍成绩规则，避免用调试包覆盖正式包。

### A7. 兼容字段填错

旧 host/kernel 题可能读取 `host_cpp`、`kernel_cpp`、`tiling_h`、`tiling_key_h`。如果模板不是这个结构，或者字段指向了错误的文件，评测可能走错路径。提交后回读详情和下载 ZIP 核对。

### A8. 提交路径与模板不一致

模板返回 `kernel.asc`，就不要提交 `code/kernel.asc`；模板返回 `op_kernel/foo.cpp`，就不要只给 `foo.cpp`。以 `template` 返回的 `path` 为准。

### A9. 额度/429 处理错误

429 时按 `retry_after_seconds` 退避；不要连续重试、换账号绕过、改包名重传。不同赛事额度不同，按官方说明。

## B. 正确性与数值

### B1. 只测一个 shape

至少测：最小、最大、非对齐尾块、单行/单列、空输入、全重复、全非法、极端重复度。尾块 mask 错一位就可能是 WA。

### B2. 输入被改写

题目通常要求输入只读。调试时为了省事原地改输入，正式版忘了恢复，会直接 WA 或违规。运行前后对输入做逐字节校验。

### B3. 输出未初始化 / 未完全写回

- workspace 没清零，累加结果带脏值；
- 只写了部分 block，尾部行没写；
- 只写 UB/L1，没写 GM；
- 多个 kernel 覆盖同一输出；
- 原子累加没同步，最后一次写丢失。

### B4. 重复索引 / 非法索引语义错误

稀疏算子里，重复索引通常要保留重数，不能简单去重；非法索引可能有特定语义（忽略、钳位、报错），以题面为准。不要假设“平台输入很稀疏/没有重复”。

### B5. 精度表达不当

- FP16 中间累加溢出/舍入；
- 该用 FP32 的地方用了 FP16；
- 归约顺序改变导致误差放大；
- 用 INT8/INT4 压缩但没证明范围；
- 近似函数（exp/log/rsqrt）误差超门；
- NaN/Inf 传播。

先看题目精度门（绝对/相对/worst/比例），不要用“看起来差不多”判断。

### B6. RoPE / KV merge / mask 等特化语义

这些语义经常有特殊折叠、清零、布局、输出合并规则。不要用通用公式擅自简化；以参考实现和题面为准。

### B7. 只测冷启动或只测热启动

冷启动可能有初始化、页表、频率爬升；热启动可能有 L2 驻留。至少记录两种，并说明采用哪种。

## C. AscendC 编程

### C1. UB/L1/L0 容量算错

- UB 物理 192KB，但可用大小受框架/对齐/双缓冲影响；
- L1 512KB，L0A/L0B 64KB，L0C 128KB；
- 多个 buffer 叠加后超限，编译可能过、运行越界；
- `InitBuffer` 的字节数不是元素数；
- 对齐要求（32B/512B）没满足。

### C2. 同步事件不匹配

- `SetFlag` / `WaitFlag` 的 event ID 或 pipe 不匹配；
- 多缓冲用了同一个 event；
- 跨核 `CrossCoreSetFlag` / `CrossCoreWaitFlag` 方向写反；
- 只在一个分支 Set，另一个分支没 Wait；
- `SyncAll` 用错（AIV/AIC 混合核时尤其危险）；
- `pipe.Reset()` 后继续用旧 LocalTensor。

### C3. 跨核就绪/完成标志的可见性

GM 标志位需要正确的 cache 操作和内存屏障；只写一个 `int` 不等于对端可见。典型组合：

```cpp
DataSyncBarrier<MemDsbT::ALL>();
flag.SetValue(idx, 1);
DataCacheCleanAndInvalid<int32_t, CacheLine::SINGLE_CACHE_LINE,
                        DcciDst::CACHELINE_OUT>(flag[idx]);
```

对端轮询时也要 invalidate 后再读。具体 API 以 CANN 版本为准。

### C4. 生产者/消费者映射假设错误

“轻核先做完就可以先消费重核的输出”不一定成立：任务可能被映射到同一个物理核/同一个 slot，或者消费者还要等第二个 batch 的生产。先打印/记录 task→core→slot 映射，再设计 wavefront。

### C5. 只优化局部，不付新增服务成本

常见新增成本：

- 多一次 GM 写回/原子累加；
- 多一次 FIX；
- 多一次布局转换；
- 多一份 workspace；
- 多一组同步/轮询；
- 任务切得更碎，尾部 underfill。

局部 busy 降低不等于完整 Task 降低。

### C6. 任务划分不均

- 64 个任务分给 40 个 AIV，必然有人做 2 个、有人做 1 个；
- 最后一个任务决定尾部；
- 重任务集中在少数核；
- 为了“早开始”把任务切碎，反而增加启动/同步开销。

### C7. 动态 shape / tiling 对齐

- tiling 结构体字段顺序/大小与 kernel 解析不一致；
- host 和 kernel 用了不同版本的 tiling header；
- `blockDim` 与实际任务数不匹配；
- 小 shape 走了大 shape 的 padding 路径，越界或浪费；
- 空 tensor / 0 维没有单独处理。

### C8. 编译宏 / 模板参数与实际路径不一致

改了模板参数但 host 仍走旧 tiling key；或者 `#if` 分支在目标编译器下没生效。记录实际 kernel 名和 tiling key，不要只看源码。

### C9. 用了目标芯片不支持的 API

本地 910B3 能编译/运行，不代表平台 910B4 支持同一指令或同一代 API。以目标 CANN 版本和芯片文档为准，必要时在目标环境编译验证。

## D. 性能与计时

### D1. 把 busy 相加当总时间

Cube、Vector、MTE、Scalar、Fixpipe 可以重叠，busy 相加会大于 Task Duration。要看关键路径、最后完成者、同步等待。

### D2. 用平均 busy 推断最慢核

平均 50% 可能意味着 20 个核里 1 个 100%、其余空。要看逐核时间线和尾部。

### D3. 本地收益直接当平台收益

本地 910B3 与平台 910B4 在频率、L2 容量、调度上可能不同；本地 +5µs 可能平台 −2µs。平台裁决前，本地收益只是筛选信号。

### D4. 只测一个输入分布

平台真实索引分布未知。只对“很稀疏/很集中/无重复”的本地输入优化，可能平台完全不走该分支。至少测 default、随机、partial、极端重复。

### D5. 计时窗口混入其他负载

多 agent 同时跑 NPU、后台 profiling、其他进程占用，都会污染结果。统一用 `npu_lock.sh`，记录频率和调用间隔。

### D6. 预热/采样策略不一致

对比两个版本时，预热次数、计时次数、丢弃策略、是否 checked、是否复用 workspace 必须一致。否则差值可能来自测量方法，不是代码。

### D7. 忽略启动/收尾

短算子常被 launch、初始化、同步、尾部主导。优化了 10µs 的计算，可能只省 1µs 总时间；反过来，减少一次同步/一次尾部等待可能收益更大。

### D8. 多 kernel 只比较一个子任务

如果候选把单 kernel 拆成多个 kernel，必须比较完整调用窗口，不能挑一个更快的子任务和旧版单任务比。

## E. 工程与调试

### E1. 跑错构建产物

改了源码但 `ASCEND_CUSTOM_OPP_PATH` 指向旧 build，或动态库缓存未刷新。记录 `.so` SHA 和实际加载路径。

### E2. 日志污染 / 性能插桩未关闭

调试 `printf`、计时 event、额外同步会改变性能。最终计时必须用无插桩版本，并做 ON/OFF 对照。

### E3. 失败日志被覆盖

每次实验用新目录/新 tag，不要覆盖旧日志。失败也是证据。

### E4. 只看最后一行错误

ACL/CANN 错误经常是连锁的；从第一个非 0 返回值、第一条 error 日志开始查。

### E5. 没有源码/产物绑定

只记录“r12 比 r11 快”没有意义，除非能证明两次跑的源码、构建、tiling key、输入完全对应。保存 SHA 和 manifest。

### E6. 清理注释当免责

规则写明注释可以作为违规证据，代码本身才是主要判定依据。不要指望删注释解决合规问题；最终版要真正删掉违规路径。

## F. 快速自查

- [ ] 题目域内任意合法输入都正确，而不只是公开样例
- [ ] 没有 host 数值计算、hash/白名单、结果重放、空 kernel、纯拷贝
- [ ] 输入只读，输出写回 GM，workspace 清零
- [ ] 重复/非法索引、空块、尾块、RoPE/KV merge 语义正确
- [ ] 同步事件、跨核标志、cache 操作成对
- [ ] 没有超 UB/L1/L0 容量，没有未对齐访问
- [ ] 本地用完整 Task 计时，ABBA/多窗口，NPU 串行
- [ ] 记录源码 SHA、产物 SHA、实际 key、频率、输入分布
- [ ] 提交前 dry-run，源码去重，SID 先落盘再轮询
- [ ] 最终版没有调试 return、临时快路径、敏感信息
