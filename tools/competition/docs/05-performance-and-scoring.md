# 平台计时、评分与本地对齐

## 1. 先搞清楚“成绩”是什么

不同赛事可能使用：

- 单点成绩：该题完整算子的平台耗时；
- 多点平均：公开点/隐藏点/全部点；
- 相对 TBest 的公式；
- 精度通过门槛 + 时间排名；
- 最近一次提交 / 历史最高；
- 全部用例 Pass 才计分，或按点计分。

**这些都以目标赛事的题面和榜单说明为准，不要从另一场比赛的公式推导。**

## 2. 平台计时的可见证据

在 CannJudge 类平台的提交详情里，`result[].msg` 可能包含 profiler 文本，例如：

```text
kernel: <KernelName>_<key>_mix_aic
Warm Up enabled. times:5

Task Duration(us): 766.039978
Task Duration(us): 781.159973
Task Duration(us): 788.179993
Task Duration(us): 787.559998
Task Duration(us): 765.619995

Block Dim: 20
Mix Block Dim: 40
Current Freq: 1650
Rated Freq: 1650
```

在已核对的一批样本中，平台单点成绩等于这 5 个 `Task Duration` 的算术平均，保留两位小数。注意：

- 这是对可见样本的核对，不是 judge 源码；
- 预热/采样流程未完全公开；
- `result[].msg` 可能挂在相邻用例行上，不能机械按行号归属；
- 频率、L2 状态、workspace 复用、输入分布都未完全暴露；
- 不能把“5 个 Task 均值”当成所有赛事的通用公式。

## 3. 本地计时口径

至少区分：

| 口径 | 说明 |
|---|---|
| event elapsed | `aclrtEvent` 记录 start/end，`aclrtSynchronizeStream` 后取差值；包含 launch 边界和同步 |
| profiler Task Duration | `msprof` 或平台 profiler 给出的单 Task 设备时间 |
| 完整调用窗口 | 一次算子调用内所有 kernel/task 的总窗口；多 kernel 时必须用这个 |
| host wall time | 进程/函数墙钟；受 Python、IO、初始化影响，不适合比较 kernel |

**不要直接换算。** 本地 event 与平台 Task 的差值可能来自：

- 频率（例如本地 1800MHz，平台 1650/1500MHz）；
- L2 容量（例如 192MiB vs 96MiB）；
- 调度/启动/同步；
- 输入分布和缓存状态；
- workspace 分配/复用；
- 平台采样和聚合方式。

## 4. 推荐的本地对比协议

### 4.1 冻结基准

每次对比前记录：

- 源码文件 SHA-256；
- 构建命令、CANN/编译器版本；
- 产物 `.so` / kernel binary SHA；
- 实际 tiling key、kernel 名、block dim；
- workspace 大小、是否复用；
- 输入 shape、seed、分布、有效边数/重复度；
- 设备型号、核数、频率。

### 4.2 ABBA / 多窗口

不要按 A-A-A、B-B-B 跑，时间漂移会混入版本差。推荐：

```text
A B B A   A B B A   ...
```

或随机化 block 顺序。每个 block 内保持预热、计时、输入、workspace 策略一致。

### 4.3 预热与采样

至少区分：

- 冷启动第一次；
- 预热 3–5 次后的稳定态；
- 连续调用窗口；
- 每次调用是否 checked（回读+比较）；
- 是否 burst（中间不回读）。

对比两个版本时，这些条件必须一致。丢弃策略要固定，不能“挑最好一次”。

### 4.4 统计

报告：

- 每个 block 的全部样本；
- 中位数、均值、最小值、最大值；
- 成对差值（同 block 内 B−A）；
- 方向一致性（多少个 block 为正/负）；
- 是否跨过噪声门。

只报“最好一次”没有说服力；只报均值可能被异常值拉偏。

### 4.5 NPU 串行

所有设备运行统一持锁：

```bash
bash tools/npu_lock.sh ./bench.sh
```

记录锁等待时间、频率、是否有其他进程。编译和 CPU 校验可以并行。

## 5. 性能账本

每个候选至少记四笔账：

1. **数学量**：MMAD/MAC、Vector 指令、归约、Convert、特殊函数；
2. **逻辑搬运量**：GM→L1、GM→UB、L1→L0、UB→GM、FIX 输出；
3. **地址与寿命**：中间 buffer 大小、生产者、最后读者、下一个写者、是否可原地复用；
4. **同步与调度**：跨核 flag、`SyncAll`、event、轮询、任务切分、尾部 underfill。

一个优化如果只降低第 1 项，却增加第 2/3/4 项，完整 Task 可能不变或变慢。

## 6. 常见“假收益”

- 局部 busy 降低，但关键路径在另一个核；
- 首个消费者提前，但最后输出没提前；
- 减少指令数，但增加了同步/重装；
- 减少逻辑字节，但地址跨度/缓存行为变差；
- 本地暖态收益，平台冷态/不同输入不成立；
- 只测公开 shape，隐藏 shape 走 fallback；
- 把 profiling/插桩版本的收益当成最终版本；
- 把不同日期、不同集成上下文的绝对时间直接相减。

## 7. 评分公式（示例，不要通用化）

某些赛事使用类似：

```text
score_i = 100 / (1 + log_1.5(t_i / T_i))
```

其中 `T_i` 是该点最优耗时。这个公式、点数、精度门槛都是**题目专属**。不要把它套到另一场比赛。

## 8. 平台提交策略

- 本地验证通过后，先 dry-run，再提交；
- 同一源码不重复提交；
- 需要 A/B 对比时，尽量同期穿插父本和候选；
- 保存每个 SID 的完整 detail；
- 平台成绩受频率、批次、输入分布影响，单次差异要谨慎解释；
- 采用哪次成绩按赛事规则；不要假设“历史最高”一定保留。

## 10. 一句话原则

**本地计时用来解释机制和代价，平台成绩用来裁决；完整 Task 永远大于局部 busy。**
