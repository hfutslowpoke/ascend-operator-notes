# CannJudge 提交规则（2026-11 版）

> 本文是我们实际提交、回读榜单和踩坑后整理的规则。
> 平台行为可能调整；以平台返回的 SID、状态和榜单为准，本文只做本地预检。

## 1. 额度

| 项 | 规则 |
|---|---|
| 每账号每天 | **50 次提交** |
| 刷新时间 | **北京时间 12:00**（UTC+8，即 04:00 UTC） |
| 账号间 | 独立额度 |
| 冷却 | 每个账号独立 |
| 提交间 | 每次提交独立，不按队伍共享 |

### 1.1 额度窗口

```text
2026-11-19 12:00 +08:00  ->  2026-11-20 12:00 +08:00
```

在 12:00 之前，仍属于前一个窗口。
**不要按自然日 00:00 统计**，否则会把两个窗口混在一起。

### 1.2 必须统计所有题目

一个账号当天可能同时在 p07、p10 等多个题目提交。
额度是账号级的，不是题目级的：

```text
账号 B 当前窗口：
  segmentmincsr  6
  randomwalk     0
  complexabs     0
  ------------------
  total          6 / 50
```

只看当前题目会严重低估。`cann_submit.py` 默认 `--quota-scope account`，会遍历该赛事所有题目。

### 1.3 2026-11-18 的实测反例

在 `2026-11-18 16:37 +08:00`，账号 B 的提交被 429。
按 12:00 窗口统计：

```text
窗口: 2026-11-18 12:00 -> 2026-11-19 12:00
B: 6 / 50
C: 1 / 50
```

B 和 C 都远没有用完 50 次，所以：

> **这次 429 不是日额度耗尽，而是短时冷却/限流。**

B 在 16:25 刚提交过一次，16:37 的 429 距上次约 12 分钟；C 在 13:29 提交过，17:08 的 429 距上次约 3.6 小时。
平台返回没有 `retry_after_seconds`，也没有 `limit_type`，所以无法确定冷却窗口。
可以确定的是：**不能用“24 次”或“51 次”去解释这次 429**。

> 另一个容易犯的错误：B 在**前一个**窗口（11-17 12:00 -> 11-18 12:00）有 54 次提交，
> 已经超过 50。11-18 12:00 刷新后，B 是新的 6 次，不是继续累计 54 次。

## 2. 429 处理

429 可能来自：

1. 日额度耗尽（先按 12:00 窗口统计）；
2. 账号短时冷却；
3. 平台全局/机房级限流；
4. 连续重试或换账号触发的反滥用。

处理顺序：

```text
1) 查 cann_quota.py，确认当前窗口是否接近 50；
2) 看 last_submission 距现在多久；
3) 保存 429 原始 body/headers 到 accepted.json；
4) 停止，不连续重试；
5) 不换账号绕过；
6) 等冷却结束或人工确认后再提交。
```

禁止：

- 每 5 分钟重试一次；
- 用 C/D 账号绕过 B 的冷却；
- 改包名、改时间戳、改 ZIP 重新 POST；
- 在 `delivery_unknown` 时盲目重发。

## 3. 同一源码去重

- 本地按源码摘要去重：同一 `source_digest` 已有记录时拒绝；
- 经验规则：**同一源码最多 2 次 POST**；超过 2 次通常没有收益，只会消耗额度；
- 确实要复投时使用 `--allow-duplicate`，并在 tag 中写清原因；
- 平台也可能按重复包处理，重复提交不等于重新评测。

## 4. 提交状态

| 状态 | 含义 | 动作 |
|---|---|---|
| `Queued` / `Queuing` / `Pending` | 排队 | 等待 |
| `Running` / `Judging` / `Compiling` / `Wait` | 评测中 | 等待 |
| `Pass` | 全部 case 通过 | 记录 SID、逐 case |
| `Wrong Answer` | 结果错误 | 修正确性 |
| `Time Limit Exceeded` | 超时 | 先看是否单 case 爆炸 |
| `Runtime Error` | 运行失败 | 看 ACL 错误码/平台日志 |
| `Compile Error` | 编译失败 | 本地 CANN 版本差异优先 |
| `Judge Interrupted` | 评测中断 | 可能不计额度；以历史为准 |

### 4.1 SID 优先

POST 成功后第一件事是保存 `submissionId`（SID），然后只 GET 详情。
如果 POST 返回没有 SID：

```text
status = ambiguous_do_not_retry
```

不要重发；先查账号历史，按源码摘要/时间/题目匹配。

### 4.2 终态才写成绩

`accepted` 只代表平台受理，不代表通过。
只有终态 `Pass` + 逐 case 结果才能写入“当前最优”。

## 5. 计分

平台单 case 分数：

```text
score_i = 100 / (1 + ln(time_i / tbest_i) / ln(1.5))
```

平台总分是逐 case 算术平均：

```text
total = mean(score_i)
```

决策时看：

| 指标 | 含义 |
|---|---|
| `gain_2x` | 该 case 时间减半，总分增加多少 |
| `factor_to_50` | 还要快多少倍才到 50 分（1.5×tbest） |
| `required_ratio_for_target` | 只靠该 case 达到目标名次所需的 time/tbest |
| `all_at_1_5x` | 所有 case 都到 1.5×tbest 时的总分上限 |

大 case 差 1000× 时，2× 改进几乎不涨分；先判断是结构问题还是参数问题。

## 6. 账号与凭据

- 账号文件：`CANNJUDGE_ACCOUNT_FILE`，权限 0600；
- 工具只读 `label/uid/cookie`，不打印 Cookie；
- 不把 `accounts.json`、Cookie、Token 写入仓库、日志、提交包或聊天；
- 账号过期时间可在 `cann_client.py accounts` 查看；
- 一个账号一个额度池；不要假设“换账号就能绕过冷却”。

## 7. 本地预检清单

提交前：

- [ ] `cann_quota.py` 显示当前窗口剩余 > 0；
- [ ] `last_submission` 距现在足够久（按经验至少 30 分钟，保守 60 分钟）；
- [ ] 源码 dry-run 通过，`source_digest` 与预期一致；
- [ ] 同一 digest 没有已受理的 POST；
- [ ] 本地 `test_local` / 扩展对拍通过；
- [ ] 已保存 plan/accepted/detail 路径；
- [ ] 用户明确授权 POST。

提交后：

- [ ] 保存 SID；
- [ ] 轮询到终态；
- [ ] 保存逐 case `time/tbest/score`；
- [ ] 运行 `cann_quota.py` 复核窗口计数；
- [ ] 更新最优/回退决策。
